# CLAUDE.md

Guidance for Claude Code (and any other agent) working in this repository.

## What this is

A Laravel-based internal ERP portal (staff_id + password login) covering seven
modules: **UAC** (user access control), **Staff** (HR directory), **Leave**
(leave requests/balances), **Letters** (document routing), **Visitors**
(kiosk check-in/out), **Assets** (ICT inventory, plus Android Enterprise
phone management — "MDM", behind `GWL_MDM_ENABLED`), and **Transport** (fleet
management). See `APP_DOCUMENTATION.md` and `docs/` for a functional
walkthrough of each module — this file is about how the code is put
together, not what it does for end users.

A **Commercial** module (billing and meter-reading analytics from Excel uploads, behind `GWL_COMMERCIAL_MODULE_ENABLED`) is
being built in phases; Phases 1 to 5b (import, reconciliation, batches, reading and billing analytics, combined analyses and exports,
settings and reminders) are in, and Phase 6, the **Customer List** (weekly/monthly `rptCustomerDetails` uploads, millions of rows),
is built behind its own flag `GWL_COMMERCIAL_CUSTOMER_LIST_ENABLED`. Design and decisions: `docs/commercial-module-design.md`;
the customer list: `docs/15-module-commercial-customer-list.md`. Phase 7 sends SMS to Accra West customers through Arkesel (behind `GWL_COMMERCIAL_SMS_ENABLED`): `docs/16-module-commercial-sms.md`.

A **Health & Safety** module (incident reporting that replaces the four Microsoft Forms; later equipment, PPE and alerts, behind
`GWL_HEALTH_SAFETY_MODULE_ENABLED`) is being built in phases; Phase 1 (sites, incident reporting end to end) is in. It is open to
every role (everyone reports), so the permissions decide what each person sees. Design, decisions and what was built:
`docs/health-safety-module-design.md` (section 8.1). Things that are easy to get wrong:
- **What a viewer may see of an incident is decided only by `Services/HealthSafety/IncidentVisibility`** (scope, reporter identity for confidential reports, injury details, findings, timeline notes). The register, detail screen, print copy/PDF, notices and photo route all call it; never filter in Blade. The Livewire `ScopesHealthSafetyByActor` trait (a third separate scoping trait) only wraps it.
- **Every change goes through `IncidentWorkflowService`**, which re-reads the incident `lockForUpdate`, authorises on that copy, writes the `hs_incident_status_logs` row and the audit entry, and fires events after the commit. High/Critical incidents close only through `pending_closure` and an `approve_closure` holder. `IncidentShow` keeps only the incident id and re-checks visibility on every call.
- Notices (`IncidentNotificationService`) reuse `GeneralDatabaseNotification` and never name a reporter.
- **Anonymous reports** (`is_anonymous`): `IncidentWorkflowService::submit()` stores no user, employee, IP or uploader for them (audit row written with no user via `audit()`, photos re-encoded by `withoutMetadata()` and renamed). Keep it that way: anything new that records "who" while a report is filed (logs, notices, timeline) must skip it for an anonymous one. Outside-authority tracking was dropped (its `hs_incidents` columns are unused).
- **Phase 2 (fire extinguishers and first aid kits):** the *computed state* of an item is written once per state as an SQL condition and a PHP test side by side (`states()` in `HsFireExtinguisher` / `HsFirstAidKit`, trait `HasEquipmentState`); never re-derive a state in a screen, a count or an export, and keep conditions NULL-safe because they are negated to exclude earlier states. Lists and the overview counts are built only by `EquipmentExpiryService`. Region/district rules live in `Services/HealthSafety/ActorScope`, shared by `IncidentVisibility` and `EquipmentScope`. Every label naming a user who acted on an incident goes through `IncidentVisibility::nameFor()` (a confidential reporter can also be its owner or closer). Equipment sits at a site OR in a vehicle (enforced in `EquipmentLocation`, no DB CHECK); it copies region/district from its site, and `Sites` save updates them. Checks and services are immutable. Import (`EquipmentImportService`) is create-only, re-reads the file on confirm and never creates a site.
- **Phase 3 (PPE):** `PpeComplianceService` is the ONE evaluator of who is missing PPE (rule in design §8.9: missing > overdue > short > replacement_due > ok); the gaps screen, My PPE and the overview all call it and it deliberately has no SQL twin. Stock is an immutable signed ledger (`hs_ppe_stock_movements`, rules in `PpeStockService`, balance never negative, `lockForUpdate` on the `hs_ppe_types` row); a correction is an `adjustment` row. Issues (`PpeIssueService`) post their ledger row in the same transaction unless `is_historic` ("already held"); a normal issue is dated today, closed issues are immutable, replacing closes the old rows and sets `replaced_by_issue_id`. A PPE store is a site with `is_ppe_store` (normally the regional office, which has no district, so district managers see issues and gaps but no balances); the employee picker is `EquipmentScope::employees()`, `EmployeeDirectory` is untouched. Details: design doc §8.11.
- **Phase 3b (QR labels and site posters):** printed codes hold an ABSOLUTE link built only by `QrLinks` (base `gwl.hs_qr_base_url`, else `APP_URL`; numeric item id, never the asset code), so labels and posters are printed from production only. The only QR code is made in `QrCodeGenerator` (bacon/bacon-qr-code, already an MDM dependency; SVG data URI, Dompdf draws it as vectors, no GD/Imagick). `EquipmentLabelService` / `SitePosterService` scope the items by the actor (outside items are excluded and counted), render first, and stamp `label_printed_at` only after the PDF exists; ticked rows reach the download route through a one-use `LabelBatch` token. `LabelController::scan` answers the same 403 page for a missing item and one outside the person's reach (do not make them differ); `?check=1` opens the existing check form and `ReportIncident` `?site=` only pre-fills. Details: design doc §8.14.

A **Regional Blog** module (articles the PR team of a region writes about its activities, meetings, workshops and training; behind
`GWL_BLOG_MODULE_ENABLED`, default on) is in. It is **not a module tab**: it is a standalone, full-page, magazine-style blog on its own layout
(`layouts/blog`, `x-blog-layout`, its own `resources/css/blog.css`, no ERP sidebar), opened **in a new tab** from the Blog link at the right of the
ERP header (`ErpNavigation::blogLink()`; the `blog` module access, the `blog.manage_posts` permission and the flag are unchanged). Every role may enter it;
the permissions decide the rest. Design and rules: `docs/14-module-regional-blog.md` (it also holds the manual QA checklist for the browser editor).
Things that are easy to get wrong:
- **What a user may see or write is decided only by `Services/Blog/BlogVisibility`**: staff read the *published* articles of their OWN region (`employees.region_id`) and nothing else, with no Head Office or manager exception; a holder of `blog.manage_posts` (the `pr_officer` role) also reads drafts and writes in their own region only; `super_admin` sees and writes every region. The same class decides who is given a picture (`canViewMedia()`) and the gallery (`scopeGallery()`). The reader pages (`BlogFeedService`), the picture route, the Livewire `ScopesBlogByActor` trait (yet another separate scoping trait, it only wraps it) and the services all start from it; never filter by region in Blade.
- **Every change goes through `BlogPostService`** (re-reads the article `lockForUpdate`, authorises on that copy, writes a saved version and the audit entry). An article or picture outside the user's region answers **404**, not 403, and the Livewire components resolve ids inside `scopeManageable()`. `lock_version` rises with every change of the content and the editor passes the version it opened: a newer one raises `BlogConflictException` (the editor warns, never overwrites silently). **Autosave touches drafts only** (`autosave()` refuses a published article). The last `gwl.blog_revisions_keep` versions are kept and restorable.
- **The body is an editor document (TipTap JSON) and the browser never supplies HTML.** `BlogContentService::process()` cleans it against an allowlist (anything else is dropped, links only `https`/`mailto`/`tel`, pictures only by media id from the region's own pictures, pictures/galleries/videos only as top-level blocks), renders `body_html` from the cleaned document with every value escaped, runs it through `symfony/html-sanitizer`, then a last check refuses any block that points anywhere but `/blog/media/{id}/{size}`; `body_html`, `body_text` and `reading_minutes` are rebuilt together on every save. **Print a body only through `BlogPost::bodyHtml()`.** Older Markdown articles stay `body_format = markdown` (raw HTML stripped, unsafe links refused) and are converted only by a save that carries the editor's document, never on read. Videos are YouTube/Vimeo by id only (the server builds the embed).
- **Pictures go through `BlogMediaService` only**: validated by CONTENT (a real JPG/PNG/WebP/GIF within the size, pixel and per-article limits; no SVG), rebuilt with GD (auto-oriented, EXIF/GPS and any payload dropped; the orientation is read from the file's bytes because the `exif` extension is not required), stored only on the private `local` disk in thumb/medium/large plus WebP, and served only by `blog.media` (`nosniff`, private cache, ETag/304). A reader is given a picture only while a *published* article of their region shows it (`blog_media.in_use`); never write a `blog_media` row or a file anywhere else. `php artisan blog:prune-media` (daily, needs the scheduler) deletes unused pictures once no saved version shows them either. Audit rows hold ids and counts, never text, captions or file names.
- Cover photos are `blog_media` rows (`cover_media_id`); an older cover is still the single private file `cover_path`, served by `blog.cover`. The editor (`resources/js/blog-editor*.js`, TipTap) is a separate Vite entry loaded only on the editor pages and the lightbox (`blog-lightbox.js`) only on article/gallery pages. The browser editor cannot be unit-tested: use the QA checklist in the module doc.
**Transport is region-scoped** (vehicles carry `region_id` + `district_id`; details and the backfill: `docs/18-transport-region-scoping.md`). Things that are easy to get wrong:
- **Which vehicles a user reaches is decided only by `Services/Transport/TransportScope`**: `super_admin` all (including unplaced vehicles, i.e. NULL region); Head Office staff only vehicles in the Head Office district; everyone else their region **excluding** the Head Office district; no employee/region, nothing. Head Office shares a region id with its staff, so never scope by region alone. Use `Vehicle::visibleTo()` / `TransportScope::vehicles()`, and `visibleTo()` (trait `ScopedByVehicle`) on expenses, mileage logs, issues, maintenance records and assignment history; never filter in Blade and never `Vehicle::find()` a client value (resolve it with `TransportScope::findVehicle()`). Out of reach answers **404**, not 403.
- **Roles are permissions, not reach**: `transport_manager` has no bypass (policy, screens, API); permission checks go through `TransportScope::can()` (`super_admin` or the permission). Group any `orWhere`/`orWhereHas` in a closure after the scope or it escapes it.
- **`TransportService` writes check the vehicle themselves** (`authorizeVehicle()`, actor defaults to the signed-in user, nobody acting writes nothing). The vehicle's location is the actor's own (only `super_admin` picks one), and a user/driver put on it must be based there (`TransportScope::personFits()`).
- `ReportsService` takes the acting user and keys its cache by `TransportScope::keyFor()`; `VehicleExpensesExport` takes the actor. `TransportNotificationService` tells only `super_admin` and the `transport_manager`s of the vehicle's location (`managersFor()`); the `transport:check-expiries` job itself reads every vehicle on purpose. The H&S equipment vehicle picker is not scoped by Transport yet.
- **The vehicle brand/model catalogue (`vehicle_brands`, `vehicle_models`; `docs/19-transport-vehicle-catalogue.md`) is changed only through `Services/Transport/VehicleCatalogService`** (create, rename, move, activate/deactivate; the vehicle form's "Add new" panels, the vehicle import and Transport > Settings all call it; never write those tables elsewhere). It is shared and NOT region-scoped, needs `transport.manage_vehicle_catalog` (checked via `TransportScope::can()` in the service, the screens, the routes and the form panels) and writes an audit row per change. `vehicles.brand` / `vehicles.model` stay plain text, so a rename or move rewrites the matching vehicles' text (soft-deleted included, old name case-insensitive, a model also by its old brand) in the same transaction; nothing is deleted, only deactivated, and the vehicle form keeps a vehicle's current brand/model selectable.

A **G-Water** module (bottled and sachet water bought from G Water and sold by each location, behind `GWL_GWATER_MODULE_ENABLED`, default off; design and as-built notes: `docs/17-module-g-water.md`) is fully built (Phases 1 to 4: prices, daily sales, trips, stock ledger, opening balance, damages, expenses, payments to G Water and the owed balance, fuel reimbursement, profit and loss with charts, Excel/PDF exports, settings, reminders, import of past records). Things that are easy to get wrong:
- **A location is Head Office OR a region WITHOUT Head Office**, and only `Services/GWater/GwaterVisibility` decides what a user reaches (it applies `TransportScope`'s one Head Office-or-region rule to the `gw_` tables; never filter by region in Blade or a screen, never scope by region alone). Another location's row answers **404**; `super_admin` reads everything but must pick the district whose books a write goes into; a login with no employee region has no books. The Livewire `ScopesGwaterByActor` trait (yet another separate scoping trait) only wraps it.
- **Every write goes through `GwaterWorkflowService`**: permission, then (inside one transaction that locks the product rows) re-read `lockForUpdate` and authorise on that copy, then the rule, then `AuditLog::record`. Never write a `Gw*` row anywhere else. Nothing is deleted: `void*` needs a reason and posts reversing ledger rows. Money is integer **pesewas** (`Money` is the only cedis<->pesewas conversion), quantities integer packs.
- **Stock is the immutable signed ledger `gw_stock_movements`** written only by `GwaterStockService` (a model hook refuses update/delete). The closing balance of every DAY must stay >= 0 (so a sale cannot be backdated to an empty shelf, and a void that would take sold packs away is refused); a void posts the same movement type with the opposite sign dated like the original, a correction is an `adjustment`. Balances are per location, never per product alone.
- **Prices: one dated list, `gw_prices`, read only by `GwaterPricingService`**: a location's own latest row dated on or before the day, else the system default (a row with no location, super_admin only). A sale, purchase line and damage freeze the price they were priced at; rows are immutable and a row that would re-price posted entries is refused. The 12 May 2026 bottle increase (25 -> 26, cost 20) is a seeded default row, so the cost did not move.
- **The Transport link is read-only and goes through `TransportScope`**: `findVehicle()` for the vehicle (404 outside reach), `VehicleExpense::visibleTo()` / `MileageLog::visibleTo()` for fuel and mileage, and a trip's vehicle and driver must be based at the trip's own location. A fuel expense links to ONE non-voided trip (DB unique; a void releases it and keeps the old id in the audit row); fuel comes from Transport OR is typed in G-Water, never both; the Transport amount is never copied (read live, `GwaterSummaryService::tripFuel()`).
- **The waybill file (picture or PDF)** is checked by content (PDF by its signature, no SVG), kept on the private `local` disk (random name) and served only by `gwater.purchases.waybill` after `GwaterVisibility::find()` (404 outside the location); never give it a URL, never put its name in an audit row.
- **Payments to G Water are recorded when paid** (`recordPayment()` takes `paid_on`; there is no request/"mark paid" step, no overdue reminder; the old `requested` rows are voided by a migration). The tile and statement label is "Opening balance".
- **Only fuel is reimbursable** (loading / offloading is one payment, paid in cash; category `loading`, legacy `offloading` rows are summed with it by `GwExpense::LOADING_OFFLOADING`). `markReimbursed()` needs `gwater.reimburse` and refuses the person who recorded the entry and the person who paid the fuel.
- **The profit and loss is worked out only in `GwaterProfitService`** (screens, charts, Overview and exports all call it; never add a second implementation, in SQL or a screen). Cost of water sold is the rolling weighted-average cost carried over the whole history; damages are written off at their frozen cost; **no price is ever read from the price list for history**, only the prices frozen on the lines (opening stock is valued on `gw_opening_balance_lines`). Fuel is the linked Transport `VehicleExpense` read live (trip date) or the G-Water fuel expenses, **counted once per trip**. Ratios are `null` on a zero denominator. The cached payload (arrays/scalars only) is keyed by the user's scope, `GwaterBooksVersion` (bumped after every workflow write) and a fingerprint of the Transport fuel rows.
- **Sales are cash or credit**: a credit sale needs a customer name and the money that comes in later is a `GwSaleReceipt` recorded by `recordSaleReceipt()` (never more than is owed; a wrong one is voided and the customer owes it again; a credit sale with receipts on it cannot be voided until they are). What a customer owes is computed only by `GwaterSummaryService` (`creditSalesOwing()` and friends: amount less receipts not voided, as at a day); revenue is recognised at the sale, `cash_collected` / `owed_by_customers` sit beside it in the P&L. The customer's name and phone are never put in an audit row, notice or log.
- **Fuel is the only reimbursable cost**; loading / offloading and other costs are paid in cash (`paid_by_user_id` on them is refused). A fuel expense already paid back cannot be voided.
- **Exports** go through `GwaterExportService` -> the Commercial `CommercialReportExport`/`ReportSheet` (text cells stay text) or the Commercial PDF page; one location per file, `gwater.export` AND `gwater.view_reports`, row caps in config, one audit row per export (ids and counts only).
- **Settings** (`GwaterSettings`) are per-location overrides of `config/gwl.php`, stored only when they differ from the default. **Reminders** (`GwaterReminderService`, `gwater:remind`, scheduled only while the module flag is on, scheduler required) send one notice per item per repeat interval (`gw_reminder_states`) carrying only product, location and counts, to active `gwater.record` holders based at the location.
- **The past-records import posts every row through `GwaterWorkflowService`** (so stock rules, waybill uniqueness, frozen prices and audit all apply); preview runs the same code in a transaction that is rolled back; confirm re-reads the file; all-or-nothing unless "valid rows only"; create-only and always the importer's own location. Do not write rows with any other path.
- The `g_water` role (ICT-assignable, not protected, not a system role) is deliberately in neither `RoleGrantPolicy::HEAD_OFFICE_ROLES` nor `REGIONAL_ROLES`: Head Office, regional and district staff can all hold it. `admin` has no G-Water access by design.

A **Finance** and an **Audit** module are ONE payment-voucher (PV) workflow shown through two modules (behind the single flag `GWL_FINANCE_AUDIT_ENABLED`; roles `finance_officer`, `finance_manager`, `audit_officer`, `audit_manager`; design, decisions and what was built: `docs/20-module-finance-audit.md`). All three phases and two change requests (manager roles, per-location catalogue, payee comboboxes, two reminder sets, demo data; then batches, assignment by the Audit manager, printing) are in. Code lives under `Services/Finance/`, tables are `fin_*`, screens are `Livewire/Finance/*` and `Livewire/Audit/*`; do not create a class called `Audit` (it would clash with `App\Support\Audit`/`AuditLog`). Things that are easy to get wrong:
- **Which vouchers a user reaches is decided only by `Services/Finance/FinanceScope`** (the Head Office-or-region rule of `TransportScope`, applied to `fin_pvs`; `super_admin` all but must pick a district to write; no employee region = nothing; another location's row answers **404**). `pvs($user, 'audit')` never includes a draft or a voided draft. Suppliers are deliberately NOT location-scoped (the category/type catalogue IS per location, below). The Livewire `ScopesFinanceByActor` trait (another separate scoping trait) only wraps it; never filter by region in Blade or a screen.
- **Roles are permissions, not reach, and the workflow service checks the permission itself** (a hidden button is only a courtesy). `finance_officer` prepares, sends, resubmits, voids, acknowledges and adds/edits/imports suppliers (NO catalogue, NO reminders, no deactivating suppliers). `finance_manager` (`finance.view`, `.view_reports`, `.export`, `.manage_categories`, `.manage_reminders`, `.deactivate_suppliers`) reads EVERYTHING of its location but cannot add, edit, send, resubmit, void or acknowledge. `audit_officer` reviews ONLY what is assigned to them (below). `audit_manager` (`audit.view_reviewed`, `.view_reports`, `.export`, `.manage_reminders`, `.assign`; no `audit.review`) assigns, and OPENS only vouchers with a tick, query or withdrawn-tick event: that is ONE condition in `FinanceScope::pvs()` (`auditReach()`: `all` super_admin, `assigned` an officer, `worked` the manager and read-only roles); a never-reviewed With Audit voucher answers 404 on the detail, file route, search and exports. The manager's only wider view is `assignmentQueue()` / `assignmentBatches()` (a LIST with `QUEUE_COLUMNS`: no payee, details, remarks or file; never a draft), which is not a door. `FinanceScope::pvsForTotals()` is for COUNTING only (analytics figures, how many are waiting, never a list). Audit has NO category/type screen, control or route (`audit.categories` answers 403).
- **Every voucher write goes through `PaymentVoucherWorkflowService`** (permission, then re-read `lockForUpdate` and authorise on that copy, then the rule, then an immutable `fin_pv_events` row + `AuditLog::record`, events and the books-version bump after the commit). Audit rows, notices and logs hold ids, statuses and counts only: never the payee, amount, comment, reason, supplier name/TIN/phone or file name. Nothing is deleted: void needs a reason, and a voided PV number is never reusable (`pv_no_key`, normalised, unique company-wide; a clash says only "already used").
- **Separation of duties**: whoever submitted a voucher in any round (`submitted`/`resubmitted` event) cannot tick, query or withdraw on it, even with both roles and even as `super_admin`. Audit can withdraw a tick only while the status is `audit_acknowledged`. `lock_version` rises on content changes (fields and files) and the form passes the version it opened (`PvConflictException`, never a silent overwrite).
- **The catalogue is per location, read and written only through `PvCatalogService`** ("own row else system default", the G-Water price pattern). The seeded categories/types are system defaults (`unit` NULL, only super_admin edits them); a `finance_manager` adds location-owned items, renames or switches off ANY item for their location only (`fin_catalog_overrides`, stored only while different from the default; a category switched off takes its types off there) and moves only their OWN types. `effective($location)` is the ONE place that works out names and on/off state, names are unique case-insensitively within a location's effective list, nothing is deleted, audit rows hold ids and the location key only. **Never print `category->name` / `type->name`**: use `effective()` for a list and `category_label` / `type_label` (`labelPvs()` for a page) for a voucher; a voucher keeps its ids and shows its location's CURRENT name. Every catalogue change bumps the books version (all locations for a default) so cached Reports/exports never show an old name. The voucher form only OFFERS active items (no add panel); management is only Finance > Settings > Categories and types (`finance.manage_categories`, checked in service, screen and route). **Blade does not compile `@js()` inside a component's attributes** (it renders literally and the click does nothing; this was the reported rename bug): send an id and read the value on the server. **Attachments** go through `PvAttachmentService` only (content-checked, private disk, random names, served only by the scope-checked routes). The marks (tick/X/clock) are computed only in `FinPaymentVoucher::marks()`.
- **Payee pickers (step C):** the shared `<x-form.searchable-select>` (ARIA 1.2 combobox; extended with `min-chars`, `limit`, a live region, Home/End and a `noMatch` slot). Employees/retirees/suppliers search SERVER-side (250 ms debounce, 2+ characters, 20 rows: `FinanceScope::searchEmployees()` stays inside the location and never mixes the kinds, `SupplierService::search()` is active only; results show staff ID + department or the supplier code, never a phone, e-mail or TIN; `%`/`_` are plain text via `FinanceScope::like()` + `ESCAPE '!'`). **Districts are region based only** (`FinanceScope::districts()`: a region's districts, not Head Office, not another region; Head Office its own; super_admin the location they picked). The browser sends back only an id, re-resolved inside the actor's scope on every save; changing the kind or the location clears the payee.
- **Suppliers (phase 2) are written only by `SupplierService`** (the Suppliers screen, the PV form's quick add and the import all call it; `SupplierImportService` is create-only and never a second writer). One company-wide list, NOT location-scoped; TIN, phone and code are optional and a blank is NULL, never `''`. A duplicate name (`name_key`) or TIN is refused naming the supplier that is there; a look-alike (`SupplierMatcher`, the only place) is a warning that must be acknowledged on the screen and a listed warning in the import. Nothing is deleted (deactivate needs `finance.deactivate_suppliers`, not given to `finance_officer`); a voucher freezes the supplier id AND name. A supplier's voucher count/total/last used come only from `SupplierDirectory` through `FinanceScope` (a location never sees another's amounts). Audit rows hold ids and field names, never a name/TIN/phone; the import writes one summary row. The "payee left service" flag is the ONE test `PayeeStatusService::evaluate()` (employee payee, not active, not a Transfer; before/on the PV date vs since), shown on the detail pages and the Audit queue.
- **Phase 3:** every figure (screens, charts, exports) is `PvAnalyticsService::report()` and nothing else: one location at a time, read through `FinanceScope::pvsForTotals()` (Audit never a draft), money in pesewas, ratios `null` on a zero denominator, cached by viewer + location + period + `FinanceBooksVersion` (bumped after every voucher write, settings save and catalogue change). "Waiting" (With Audit / Queried / Audit acknowledged, since when, overdue by the location's limits) is defined ONLY in `PvBacklog` (drafts only via `PvBacklog::drafts()` for the Finance reminders). Exports are `FinanceExportService` -> Commercial `CommercialReportExport`/`ReportSheet` (text stays text) or the Commercial PDF page, need `{module}.export` AND `{module}.view_reports`, one location per file, row caps in config, one audit row of counts per download.
- **Reminders are TWO independent sets** (step D), each changed only by its own manager, per location, as overrides of `config/gwl.php` stored in `fin_settings` only when different from the default (`ModuleReminderSettings` base; `FinanceSettings` and `AuditSettings` are singletons; audit rows hold ids and the changed key NAMES, never values). Finance (Finance > Settings > Reminders, `finance.manage_reminders`): on/off, days Queried, days Audit-acknowledged, days a Draft may sit unsent, repeat; command `finance:remind` (`FinanceReminderService`); recipients are `finance.create_pv` / `finance.acknowledge` holders at the voucher's location. Audit (Audit > Settings > Reminders, `audit.manage_reminders`): on/off, days With Audit (also the Reports' "overdue" for Audit), repeat; command `audit:remind` (`AuditReminderService`); recipients are `audit.review` holders. A finance_manager cannot see or change the Audit set and the other way round (one locked-`module` component, permission re-checked in the service). Both are scheduled daily 08:00 while the flag is on (scheduler required); `fin_reminder_states` dedupes per voucher + wait + repeat interval; each recipient gets ONE digest notice per location and kind with the count, the longest wait and the PV numbers (ten at most), never a payee, amount or comment.
- **Batches (change request 2) are a CONTAINER, not an approval unit** (`fin_pv_batches`, `FinPvBatch`, docs section 10): Audit still ticks or queries each voucher on its own. **Every batch write goes through `BatchWorkflowService`** (permission, `lockForUpdate` re-read, authorise on that copy, rule, immutable `fin_batch_events`, audit row of ids and counts, events after the commit); the number `BT-<code>-<year>-NNNN` comes from `fin_batch_counters`, never typed; a voucher is in at most one batch; membership is frozen once sent; sending is ALL OR NOTHING (`PaymentVoucherWorkflowService::sendProblems()` for every member first, `BatchSendException` lists the failures; each voucher gets its own `submitted` event carrying the batch id); a draft in a draft batch is sent or voided only after it is taken out. **A batch has no stored progress: its state is `FinPvBatch::computeState()` and nothing else (no SQL twin, never re-derived in a screen, count or export)**. `FinPaymentVoucher::batchBlocker()` is the one "can it be batched" rule and sentence.
- **Assignment (change request 2):** nobody in Audit can work on a voucher until the manager assigns it (`PaymentVoucherWorkflowService::assign()`, whole batches and selections through `BatchWorkflowService`, only while With Audit, `assigned` / `reassigned` events). The officer must be an active `audit.review` holder BASED AT the location who never sent the voucher (`FinanceScope::assignableOfficers()` is also the picker). **Tick, query and withdraw need `audit.review` AND `assigned_to_user_id` = the actor, super_admin included** (an unassigned or someone else's voucher is a 404 to an officer); a resubmit stays with the same officer; an officer also reads vouchers THEY ticked, queried or withdrew on (not ones they merely sent); `batches($user, $as)` is the batch twin of `pvs()` (an officer's batch count, total and state are only their own vouchers); `batchesForTotals()` is for counting only. Vouchers sent before the migration have no officer and show as Awaiting assignment. Bulk acknowledge is per voucher (one event each); a query is never bulk.
- **Printing (change request 2):** `PvPrintService` holds ALL the wording of a print (the Blade view only lays out its arrays; a test enforces it) and prints only what the screens' own `FinanceScope` reach allows (404 outside; the manager no unworked voucher, an officer only theirs); one audit row of ids and counts per print and `print_count` on every voucher/batch printed, written only after the PDF exists; "Print selected" hands ids over by a one-use `PrintSelection` token, never the URL; cap `gwl.fin_print_max_vouchers`. The words of an amount reuse `LeaveLetterService::numberToWords()`.
- **Analytics and reminders (change request 2):** the assignment, batch and per-officer figures are in `PvAnalyticsService` and nowhere else; `officers` is the Audit manager's and Finance manager's view only (`seesOfficers()`, part of the cache key). `PvBacklog::auditItems()` splits With Audit into `unassigned` (reminds the `audit.assign` holders after `AuditSettings::UNASSIGNED_WAIT`) and `officer` (reminds ONLY the assigned officer after `AuditSettings::WAIT`, counted from the assignment); the Reports keep the single `audit` kind. The Finance set is unchanged.
- **Demo data (step E):** `php artisan finance:demo-data [--with-users] [--remove]` and `FinanceAuditDemoSeeder` (not in `DatabaseSeeder`) are `FinanceDemoDataService`: they refuse in production and unless the flag is on (`--with-users` local/testing only), make ~25 "(Demo)" suppliers and 60 `DEMO-<LOC>-0001` vouchers per location THROUGH the real services with the clock set back and notices suppressed, acting as demo staff accounts `DEMO-<LOC>-FO|FM|AO|AO2|AM` (active while the history is made, because an assignment needs an active officer, then switched off unless `--with-users`, which prints random passwords once and sets `must_change_password`), make five demo batches per location from vouchers the plan already had (a draft, awaiting assignment, in progress, completed, and one split across two officers; some single vouchers stay unassigned), skip if demo vouchers exist, and `--remove` deletes ONLY the demo rows (direct deletes where the immutable event hook blocks), batches and their events included, and puts the batch-number counters back. Never point it at a database you care about without meaning to.
- Staff exit data used for the retiree payee: `employees.is_active`, `deactivation_reason` (a `transfer` is not leaving service) and `deactivated_at`; Staff was not changed. `NotifyPvParties` is found by event discovery: do not also register it in `AppServiceProvider` (it would notify twice).

## Key conventions

### Naming
- Tables and columns: `snake_case`. Models: singular `StudlyCase` matching Laravel defaults, with a few explicit `protected $table` overrides (`AgentReport` -> `agent_reports`... actually inferred correctly, but `IctAsset` -> `ict_assets`, `ModuleAccess` -> `module_access` are set explicitly since they don't pluralize cleanly).
- Route names: `{module}.{action}`, e.g. `staff.toggle-status`, `leave.export.approved.excel`, `uac.users.invite`. Route groups set the prefix and `name()` once per module in `web.php`.
- Permissions: `{module}.{action}` slugs, e.g. `staff.manage_departments`, `transport.view_reports`. Defined as rows in the `permissions` table (module column = one of `Permission::MODULES`), not as code constants beyond the module list itself.
- Middleware aliases used in routes: `auth`, `active` (EnsureUserIsActive), `module:{slug}`, `role:{role1,role2}`, `permission:{perm1,perm2}` (OR semantics — any one match passes).

### Authorization is layered, not single-source
1. Route middleware (`module:`, `role:`, `permission:`) — first line of defense.
2. Controller-level re-check via `App\Http\Controllers\Concerns\EnforcesModuleAccess` (some controllers only).
3. Livewire component re-check via `App\Livewire\Concerns\EnforcesModuleAccess` (a **separate, duplicate trait** — don't assume changing one changes both).
4. `super_admin` bypasses every check at every layer.
5. ICT Team users without admin/super_admin are location-scoped: in UAC to Head Office or one region (`User::ictScope()`, decided in `Services/Uac/RoleGrantPolicy`), in Assets/MDM by `region_id`. `isRegionScopedIct()` helpers still exist there as thin wrappers of `User::isScopedIct()`. In Assets, reading is wider than writing: list/dashboard queries use `scopeAssetsForViewing()`/`scopeReportsForViewing()` (Head Office ICT sees every region), while create/edit lookups use `scopeAssetsForActor()` (own region) and MDM stays on `MdmAccessGuard` — keep new list screens on the former and new write paths on the latter. Head Office is a *district* whose staff share the Head Office district's `region_id`, so never scope "Head Office" by region alone.

When adding a new protected screen, replicate this pattern rather than relying on route middleware alone — several existing controllers do the belt-and-suspenders check deliberately.

### Service layer pattern
Controllers and Livewire components stay thin and delegate to `app/Services/{Module}/*`. Follow the existing per-module split:
- `Services/Leave/` — `LeaveApprovalChainResolver`, `LeaveWorkflowService`, `LeaveBalanceService`, `LeaveEntitlementService`, `LeaveNotificationService`, `LeaveHrContactService`, `WorkingDaysCalculator` — one class per concern, not one god-service.
  - **Approval routing lives only in `LeaveApprovalChainResolver`** (`route()` for who, `canAct()`/`actionableRequests()` for who may act and the queue). Approvals, AllRequests, HomeSummaryService and ManagerDashboard all use it; don't re-derive a queue from `manager_id`. Rules and the routing table: `docs/06-module-leave.md`.
  - `LeaveWorkflowService::recommend()`/`finalDecision()` re-read the request `lockForUpdate` inside a transaction and authorize on that copy; keep any new action on that pattern. `manager_id`/`approved_by_id` are employee ids, `manager_user_id`/`chief_user_id` are user ids, `is_single_stage` marks a manager applying directly to the level above (its `manager_recommendation` is `Recommended` from submission).
  - Every leave email/in-app notice goes through `LeaveNotificationService` (email switches `gwl.leave_email_notifications_enabled` / `gwl.leave_hr_email_notifications_enabled`, both checked only there; mail failures are caught and logged). Head Office is a district, so HR scope comes from `location_type`, never `region_id` alone.
  - **Annual entitlement lives only in `LeaveEntitlementCalculator`** (pure: gross by grade and tenure, compulsory deduction, net; numbers in `config/gwl.php`). Never hard-code 31 (or 26/36) anywhere else: ask `AnnualEntitlementService` (storage in `leave_entitlements`, idempotent `generate()`, `recalculate()` on grade/hire-date/location/compulsory-days changes; days already used are never taken back) or `Employee::annual_leave_days`. Staff with **no grade** keep the flat 31 and no compulsory deduction by design; contract staff (Charwoman) have no leave (`LeaveWorkflowService::guardEligible()`). Compulsory leave (`compulsory_leave_periods`, `CompulsoryLeaveService`, Head Office HR / `admin` / `super_admin` only) comes off the *gross* entitlement and is never charged to `used_days`; years done by the old `compulsory_leave_deductions` screen read as 0 so nothing is deducted twice. Details: `docs/06-module-leave.md`.
- **Grade** (`employees.grade`, `App\Enums\StaffGrade`) fixes `employees.category` (`Employee::saving`); never store a category that contradicts a grade, and read the allowed grades only from the enum (form, import, filters, reports all do). Staff without a grade are normal legacy records, not errors.
- `Services/Hr/HrAnalyticsService` — HR workforce analytics (milestones, headcount, turnover, distribution, exits, grades). It owns its scope (super_admin/admin/hr_headoffice: all regions, hr_region: own region, anyone else 403; super_admin accounts never counted), all the date arithmetic (`$asOf`), and short caching (`gwl.hr_analytics_cache_seconds`); a Transfer exit reason is shown but never counted as an exit. Details: `docs/12-hr-analytics.md`.
- **Leave approval letters** (`docs/13-leave-letters.md`): wording, date formats and number-to-words live only in `LeaveLetterService` (never Blade); `leave_letters.snapshot` is frozen at generation and only reference_no, cc, signatory mode and the Christmas line change, before the first print (each PDF response counts as a print). Signatures go through `SignatureService` only: encrypted on the private `leave_signatures` disk, never logged, audited, emailed or listed, rendered only in the PDF, and only their owner can apply one; Global Admin/super_admin may only revoke. Acting approvers are resolved in `LeaveApprovalChainResolver` (`LeaveActingAssignmentService`) for the final-approver posts only.
- `Services/Letters/LetterWorkflowService` — routing/dispatch/remark logic.
- `Services/Assets/AssetAssignmentService` — **the only writer of who holds a device** (`ict_assets.assigned_to_employee_id`) and of `ict_asset_assignments` (model `IctAssetAssignment`, one row per spell; unique `(ict_asset_id, is_current)` allows one open row). `assign()` / `reassign()` (handover) / `correct()` (picked the wrong person) / `unassign()`; `AssetRecordService::save()` hands the holder to `change()`, and swapping one person for another needs a kind (`reassigned` | `correction`). "Previous assigned to" is DERIVED (`IctAsset::previousHolder()`: latest closed row ended `reassigned` or `unassigned`, never `corrected`); `ict_assets.previous_assigned_to_employee_id` is no longer written or read and can be dropped once the history has been trusted for a while. The column is the fast "holder now" for filters and exports and always agrees with the open row. Marking an old row a correction needs `assets.correct_assignments` (super_admin by default). Audit rows hold ids and codes only.
- `Services/Assets/AssetImportService` — **Assets > Upload assets** (`assets.import` + `assets.create`, `AssetImportController`): create-only bulk upload of the `asset` category through `AssetRecordService::save(..., $audit = false)` and `AssetAssignmentService`; ONE `import_assets` audit row of counts and a batch id. `analyze()` is the only place the row rules live and BOTH preview and confirm call it: confirm re-reads the stored file (the session holds only its token, bound to the user) and never trusts rows from the browser. The region is always the importer's own (a location must be a district of it; no region column exists), manufacturer/model must already exist (never created), formulas (`=...`) are refused, xlsx only, `gwl.assets_import_max_mb` / `assets_import_max_rows`. See "Android Enterprise (MDM)" below and `docs/assets/mdm.md`.

Never update `employees.district_id`/`location_type` with a raw query: it skips that.

Its `applyFilters()` also takes `grade` (`none` = no grade yet) and `region_id`, which is how dashboard cards link into the staff list (`AllEmployees` keeps its filters in the URL).
- `Services/Staff/StaffReportService` — Staff Reports (renamed from "Staff Leave Reports"; the `staff.reports` route and `staff.view_reports` permission keep their names): leave and headcount charts, the category/grade breakdown and the Excel export. - `Services/Uac/RoleGrantPolicy` / `RoleAssignmentService` — **all** role-management rules (tiers super_admin > Global Admin (`admin`) > ICT > others, ICT location scope, `roles.ict_assignable`/`is_protected`, role↔location fit, anti-escalation) live here; UacController, the roles screen, the users import and the Head Office transfer rule (`EmployeeObserver`) all call it. Editing a user diffs roles and only touches the ones the actor may manage. **ICT Manager** (`ict_manager`, `User::TIER_ICT_MANAGER` between Global Admin and ICT team): a scoped ICT account (`User::isScopedIct()` covers both ICT roles, so Assets/MDM/UAC scoping needs no second rule) that also never sees `admin`/`super_admin` accounts, employees, roles or audit rows (`User::isIctManager()` inside the same `visibleTo()` scopes; the audit filter is `AuditLog::withoutAboveIct()`), never changes its own roles (`targetDenial()`), nobody below Global Admin manages an ICT Manager, and `ictManagerRoleDenial()` stops it granting or removing tiered, protected or Head Office-only roles whatever `ict_assignable` says. The roles screen is a read-only list for it (`rolesQueryFor()`). super_admin is invisible to everyone else via the `visibleTo($viewer)` scopes on `User`/`Employee`/`Role`/`AuditLog` (operational pickers keep `visibleInErp()`); start any list, count or export of audit rows with `AuditLog::visibleTo()`. Details: `docs/04-module-uac.md`.
- `Services/Commercial/` — the two report importers (`ReadingSummaryImportService`, `BillingSummaryImportService`, both on `ReportImportService`), reached through `CommercialImportService`; `ReportFileReader` (every sheet as a raw grid, cells found by LABEL never by coordinate), `LocationMatcher` (region/district text -> record, then `commercial_location_aliases`), `BatchLifecycleService` (void; recomputes imported/superseded), `BatchResolutionService` (resolve alias / link reader / re-match). Things that are easy to get wrong:
  - **The reports are pre-aggregated exports, not tables**, so `DataImportService`/`RawRowsImport` are deliberately not used (`RawRowsImport` only reads the first sheet). A file whose rows do not add up to its own totals is **blocked**; an unmatched reader/district only **warns** and is resolved afterwards.
  - Rows are immutable snapshots tied to a batch. Read them through `scopeEffective()` on the stat/route/band/strength models (latest non-voided batch wins), never straight off the table; `status` imported/superseded is only a label recomputed by `BatchLifecycleService::refreshStatuses()`. Compare dates with `DATE()`/`whereDate`: the `date` cast is stored as `2026-06-01 00:00:00` on SQLite.
  - **Verified against the real exports** (June-Sep 2025 reading, Jun-Aug 2026 new-service billing): the reading file's `Document map` sheet declares a used range out to column XFC and exhausts memory if loaded, so `ReportFileReader::readSheets()` lists sheet names first and never loads it; the filter block is ONE multi-line cell (`ReportFileReader::labelValue()` splits lines); reader sheets are named `Sheet2`.. and use two-row headers (`Verified`/`Strength`, `Read` over `#`/`%`); the grand-total sheet has overall Read/Skipped/Visited only, no month rows (a per-month grand sheet is also reconciled month by month).
  - **Reading analytics (Phase 2)** live in `ReadingAnalyticsService` (R1-R13 as pure passes over the already-scoped effective rows; the Livewire component owns scoping and filters, like `AssetSummaryService`). Rates are percentages and `null` on a zero denominator; the current calendar month is "in progress" and is excluded from movement/inactive/workload/consistency/outliers/scorecard. Reader-level screens (`Reading` tabs Readers/Exceptions/Scorecard, `ReaderDetail`) are individual staff performance: `commercial.view_reader_performance`, checked per tab and per reader (403 for another region's reader). Coverage uses the region-wide strength, so it is hidden under a district filter.
  - **Billing analytics (Phase 3)** live in `BillingAnalyticsService`, one snapshot at a time (`snapshots()` = newest non-voided batch per region/segment/period; never sum snapshots: balances roll forward). Every district/snapshot figure is a sum of route figures with the ratio recomputed from the sums, never an average of route ratios. `customers_count` is stored but never used or shown (its meaning is unconfirmed). A multi-month snapshot is usable on its own but excluded from compare/trend; a negative balance is a customer credit (confirmed by the Commercial team on 2026-10-12), so say so plainly, with no "to be confirmed". The `Billing` screen falls back to the default snapshot for an id outside the user's regions instead of 403ing.
  - **Combined analyses and exports (Phase 4):** `CommercialInsightsService` (C1 district scorecard, C2 estimation vs skip rate, R14 month-to-date pace, C3 summary) reuses the two analytics services and never re-implements their maths. Billing is a customer segment while reading covers everyone, and reading by district is the reader's HOME district: any screen or export that sets them side by side carries those notes, projections say "indicative", correlations appear only from 6 pairs and are never "causal", and snapshot times are UPLOAD times. Exports go through `CommercialReportData` (same scoped queries as the screens, via `ScopesCommercialByActor`) -> `CommercialExportService` (titled tables) -> `CommercialReportExport` (Excel; `ReportSheet` is a string value binder so reader names / route codes starting `= + - @` stay text) or the Dompdf view; the one route `commercial.export` needs `export_reports` plus the report's own permission (readers: `view_reader_performance`), is audited, and is capped by `commercial_export_max_rows`.
  - **Settings and reminders (Phase 5):** the editable targets and thresholds are overrides of `config/gwl.php` stored in `commercial_settings` and laid over the config at boot by `CommercialSettings::applyToConfig()` (`AppServiceProvider`), so analyses and exports keep reading `config('gwl.commercial_*')` and never the table; a value saved equal to its default is stored as no override, and the edit screen needs `commercial.manage_settings` (super_admin by default). Upload reminders (`UploadReminderService`, `commercial:remind-uploads`, scheduled only while the module is on and needing the scheduler running) tell the officers of a region, in-app, when its latest non-voided upload of a type is older than the configured days, at most once per repeat interval.
  - **Phase 5b:** the defaults come from a pristine copy of `config('gwl')` kept by the `CommercialSettings` singleton (never a `require` of the config file), so `config:cache` cannot change them; after editing `.env` on a server run `config:cache` again. Users without `view_reader_performance` see no reading figures for a home district with fewer than `commercial_min_readers_for_district_figures` distinct active readers (decided in `ScopesCommercialByActor::hideSmallGroups()`, applied in `CommercialInsightsService::districtScorecard()` and `CommercialReportData::readingTrend()`, so screens and exports agree). PDFs have their own row cap (`commercial_export_pdf_max_rows`), and the Settings screen previews how many routes the typed exception thresholds would flag (`BillingAnalyticsService::exceptions($routes, $thresholds)`).
  - **KPIs against targets (`CommercialKpiService`, screen `Commercial > KPIs`)**: the district table (sales = volume, billing, collection, arrears) with efficiency = actual / target x 100 and the arrears-and-age table. Figures come only from single-month billing snapshots (never a multi-month period, never summed across snapshots) through `CommercialReportData::kpis()`, which the screen AND the Excel/PDF export call, so they cannot disagree. Targets are YEARLY: one row per district, KPI and calendar year in `commercial_district_targets` (`effective_from` = 1 January of the year, the ANNUAL figure; nothing carries over to another year), and a month's target is annual / 12; no target = blank efficiency, never a guess; the region target is the sum of the districts' and is blank unless every district has one. Year to date = the months uploaded this year against annual x months / 12 (a month never uploaded does not count against the district). The chart numbers come from `CommercialKpiService::charts()`, built from the same scorecard as the table. A negative balance is a customer credit (confirmed 2026-10-12): ARREARS = what customers owe, credits are never netted off (exact from the month's Customer List upload where there is one, else from the billing routes' positive closing balances). The age-of-arrears formula (arrears / that month's billing) is a working definition, not confirmed.
  - **Customer list (Phase 6, `Services/Commercial/Customers/`, flag `GWL_COMMERCIAL_CUSTOMER_LIST_ENABLED`, `docs/15-module-commercial-customer-list.md`)** — millions of customers and personal data; judge every change by "does it stay fast at 5-10 million rows?". Things that are easy to get wrong:
    - **Never read these files with PhpSpreadsheet / `ReportFileReader`** (42 s and 312 MB for 18k rows): `XlsxStreamReader` streams them in flat memory; `CustomerListParser` finds everything by label; `CustomerImportService` is the resumable pipeline (locate -> stage -> reconcile -> merge -> missing -> rollup -> complete), run by `ProcessCustomerListBatch` (a queue worker is required). Progress/resume points live on `commercial_customer_batches`; one batch per district at a time (cache lock).
    - **`commercial_customers` is the CURRENT state, written only by set-based SQL** (`CustomerMergeService`): one diff pass finds the staged rows that need work, an unchanged row (equal `attributes_hash`) is never written, accounts a file no longer lists get `missing_since_batch_id` and are never deleted, `updated_batch_id` (not "last seen") is the batch that last wrote the row. Never update `commercial_customers` row by row or with Eloquent. Money is integer pesewas. The only driver-specific SQL is in `CustomerSql` (MySQL `UPDATE ... JOIN` vs `UPDATE ... FROM`).
    - **Dashboards read only rollups** (`CustomerAnalyticsService`; district-level table by default, the route-level table only for a route filter/breakdown), **never** `commercial_customers`. Only `CustomerListService` (lists, search, one customer) reads the customers table: keyset pages with row-value comparisons, ONE table per query (no joins to the lookups: MySQL then drops index order), region restriction in every query. Add a new analysis by adding a measure to the rollup build, not by querying customers.
    - **Rollback**: pre-images of rewritten rows go to `commercial_customer_undo` (kept for the newest `commercial_customer_undo_keep_batches` batches per district); only the NEWEST batch of a district can be voided (`CustomerBatchLifecycle`), exactly. Contact details are not rolled back.
    - **Personal data**: name, address, phone, e-mail live in `commercial_customer_contacts` (and transiently in staging and the uploaded workbook, both deleted when a batch finishes). Never put one in an audit row, log, exception, notification, queue payload or rollup. Lists/exports mask phones and e-mails; only `view_customer_details` holders see names; unmasking one customer is audited. Region scope: `ScopesCommercialByActor` (screens) and `CustomerScope` (jobs/commands), pinned together by a test. Exports go through `CustomerExportService` and must build **string cells** (OpenSpout's `Row::fromValues` turns `=...` into a formula).
    - **Coverage and efficiency (tab J, `CustomerAnalyticsService::coverage()`):** the eligibility rules are written ONLY there (eligible = billing accounts; a valid bill = dated in the last 30 days and above zero; metered = working or faulty meter; a read = last read date in the last 30 days; arrears = what customers owe, credits never netted off). It reads batches with `rollup_version >= 2` only (older rollups lack `billed_valid_30` / `debit_no_pay_N` and are left out and counted, never shown as zero). A new measure goes into the rollup build, never into a query on `commercial_customers`.
    - **Consumption history (`CustomerConsumptionHistory`, table `commercial_customer_consumption_history`, design 8.27):** one narrow row per billing account and MONTH (the latest upload of a month replaces it), written in the rollup phase of an import and never anywhere else; it holds the file's average consumption, no personal data. The own-history baseline (mean of the earlier months in the window, from `commercial_customer_history_min_months`) is defined ONLY in `baselineSql()`; the spike / drop / zero counts are rollup measures (`hist_*`) and drill lists (`consumption_*` issues in `HISTORY_LABELS`, deliberately NOT in `QUALITY_LABELS`, which drives the quality tab). Zero counts before enough months are stored mean "nothing to compare with", never "no anomalies". Never read the history table from a screen.
    - **Mobile numbers (Phase 6b):** a Mobile cell is read ONLY by `CustomerValues::readPhones()` (separators, 233/+233/00233/lost-zero repairs, run-together numbers cut only when one way fits, placeholders invalid); `phone_primary` and `phone_secondary` are both searched and both counted by the shared-mobile list, and a third number lives only in `mobiles`. Never test a phone with `phone_primary` alone.
    - The benchmark command refuses anything but a scratch database whose name contains `bench`; never point it at the real one.
  - **SMS to customers (Phase 7, `Services/Commercial/Sms/`, flag `GWL_COMMERCIAL_SMS_ENABLED`, `docs/16-module-commercial-sms.md`)** — messages Accra West customers through Arkesel; personal data and money, so judge every change by "could this send twice, or message someone outside Accra West, or leave a number somewhere?". Things that are easy to get wrong:
    - **The region lock lives only in `SmsAccess`** (flag + region names resolved at run time + permission; Head Office staff share Accra West's region id and are NOT let in; Global Admin only if they work there). Every screen, action, job, command and the webhook asks it, and the audience queries add the region condition themselves. Another region's campaign is a 404.
    - **Groups are defined only in `SmsAudienceResolver`** (never in Blade/Livewire): region lock, not missing from the file, a valid first number, one SMS per number; a single-table query on `commercial_customers` by keyset, contacts by id list. Unconfirmed status codes are not groups.
    - **No number outside send time.** Recipients are `customer_id` + status (no phone column); numbers are read in `SmsCampaignService::deliver()` in memory; the message TEMPLATE is stored, never the merged text; no queue payload (campaign id only), audit row, log, exception, notification or export holds a number, a name or a message (tests scan every table and log).
    - **Claim before send.** `pending -> claimed` is ONE atomic UPDATE carrying a token, before `SmsGateway::send()`; a claimed row that never got its result becomes `unknown` and is never retried; a timeout is `unknown`, only a refusal is `failed`. State changes only in `SmsCampaignService` (re-read `lockForUpdate`, authorise on that copy, audit). Tests bind `Tests\Support\Commercial\FakeSmsGateway`; nothing reaches Arkesel. Arkesel response shapes are unverified and parsed only in `ArkeselGateway`.
  - The source's percentages, `Unvisited` and `Collection Ratio` are never stored (they are measured against the whole region); recompute from counts. The `00000` System Administrator account is kept (`match_status = system_account`) but excluded via `CommercialReadingStat::scopeReaders()`.
  - Region scope is `Livewire\Commercial\Concerns\ScopesCommercialByActor` (a third, separate scoping trait: super_admin/Global Admin/Head Office see all, everyone else their own `employee->region_id`). Every `BatchShow` action re-checks permission AND region.
  - Tests build small synthetic workbooks with `Tests\Support\Commercial\ReportWorkbooks` (never commit real exports; they hold staff names and customer routes). PhpSpreadsheet's `fromArray()` needs `strictNullComparison = true` or it drops zeros.
- `Services/GWater/` — `GwaterVisibility`, `GwaterPricingService`, `GwaterStockService`, `GwaterWorkflowService`, `GwaterSummaryService`, `GwaterProfitService` (the only P&L evaluator), `GwaterExportService`, `GwaterSettings`, `GwaterReminderService`, `GwaterImportService`, `GwaterBooksVersion`, `Money` (see the G-Water box near the top).
- `Services/Transport/TransportScope` (who reaches which vehicle, see the Transport box near the top), `TransportService`, `TransportNotificationService`.
- `Services/Import/DataImportService` — shared xlsx import/preview/validate pipeline for both the UAC and Staff import screens (see `ImportController`).
- Flat `Services/ReportsService` — date-range resolution + payload building for transport reports (PDF/Excel).

If you're adding meaningful business logic, put it in a new or existing service class, not directly in a controller/Livewire method.

### Android Enterprise (MDM) — things that are easy to get wrong
- **Feature flag.** `config('gwl.mdm_enabled')` (env `GWL_MDM_ENABLED`, default false, true in `phpunit.xml`) is checked where the routes are registered (`web.php`, like Commercial), in the `routes/console.php` schedule, in the sidebar `can` closures, on Livewire `mount()`, and at the top of every `mdm:*` command. Routes register at boot, so a "flag off" test must rebuild the app with an env override (see `AccessAndFeatureFlagTest`).
- **Two separate route groups on purpose.** MDM routes live in their own `assets/mdm` group (`role:super_admin,admin,ict_team`), not inside the main Assets group, because `admin` may use MDM but nothing else in Assets and a nested group cannot loosen its parent's `role:` check. `ErpNavigation::assetsLandingRoute()` sends `admin`'s Assets tile to the MDM dashboard.
- **The webhook is `POST /webhooks/android-management`** in `web.php` with `->withoutMiddleware('web')` (no session, no CSRF) and `throttle:mdm-webhook`. It authenticates by Google OIDC + secret `?token=` and must never call Google or do device work; it stores an `mdm_events` row and dispatches `ProcessAndroidNotification`. Do not reuse the `api_token` scheme.
- **Region scope for MDM is `MdmAccessGuard`** (the service-level twin of the Livewire `ScopesAssetsByActor` trait; jobs have no `Auth::user()`). `ScopingParityTest` pins the two together. Resolve every device/asset id through it; never `MdmDevice::find($id)` from a client value. Commands re-check scope and permission again inside the queued job.
- **A queue worker and a per-minute scheduler are required** — MDM is the first thing that needs either. Tests use `sync`, so use `Queue::fake()` when you need to assert dispatch.
- **Tests never reach Google:** bind `Tests\Support\Mdm\FakeAndroidManagementGateway` / `FakeIdTokenVerifier` (see `Tests/Feature/Assets/Mdm/Concerns/BuildsMdmFixtures`). `AndroidManagementClientTest` drives the real client through a Guzzle mock (record in the *handler*, not a middleware: Guzzle runs middleware in insertion order, so an earlier one never sees Google's auth header).
- **Google enum values are SHOUTING_SNAKE_CASE; `Str::headline()` spells them out letter by letter.** Use `App\Services\Assets\Mdm\Labels`.
- Wipe is `devices.delete`, not `issueCommand` (AMAPI also has a `WIPE` command type; deliberately unused). `mdm_device_commands.payload` is encrypted and secrets (the reset passcode) are blanked after delivery; never put them in audit metadata.
- The seeded "GWL Standard Phone" policy exists in every test database (a migration creates it) — don't assert global policy counts.

### Audit logging
Any mutating action a human should be able to trace back later calls `AuditLog::record(...)` (static helper on the model) or the `App\Support\Audit::log(...)` wrapper — both write to `audit_logs`. Follow this pattern for new create/update/delete/export endpoints; it's checked for in several existing tests indirectly via the UAC audit log screen.

### Migration conventions
- Never edit an existing migration once merged — add a new `add_x_to_y_table` / `create_x_table` migration instead. The history is full of these (`add_full_name_to_users_table`, `add_must_change_password_to_users_table`, etc.).
- New/altering migrations defensively check `Schema::hasTable()` / `Schema::hasColumn()` before acting, so they're safe to re-run against a partially-migrated DB.
- Foreign keys are explicit about delete behavior: `restrictOnDelete()` for people/lookup data that shouldn't silently vanish, `cascadeOnDelete()` for child/detail rows, `nullOnDelete()` for optional links.
- Granting a role access to a new module, or adding a new permission, is done by data-seeding **inside a migration** (`DB::table('permissions')->updateOrInsert(...)`, `DB::table('module_access')->updateOrInsert(...)`), not only in `database/seeders`. Follow this pattern so a fresh `migrate` and an existing `migrate` on a running DB end up in the same state.
- UUIDs: only the Transport-module models (`Vehicle`, `MileageLog`, `VehicleIssue`, `MaintenanceRecord`, `VehicleExpense`, `VehicleAssignmentHistory`) use a `uuid` column via the `App\Models\Concerns\HasUuid` trait, and `Vehicle` uses `uuid` as its route-key (`getRouteKeyName()`). Everything else uses the numeric `id`.
- Soft deletes: only `Vehicle` uses `SoftDeletes`. Nothing else does — don't assume `deleted_at` exists elsewhere.

### Custom config
`config/gwl.php` and `config/gwcl.php` hold app-specific env-driven settings (auto-checkout time, leave carry-over expiry window, import failure threshold, the `mdm_*` Android Enterprise settings, etc.) — these are **not** stock Laravel config files, they were added for this app. `gwcl.php` currently exists mostly as a legacy/fallback alias for one `gwl.php` key; prefer adding new settings to `gwl.php` and reading them as `config('gwl.your_key')`.

## Testing

- Plain PHPUnit, not Pest. Test suites are `tests/Unit` and `tests/Feature` (see `phpunit.xml`); in practice almost all coverage is under `tests/Feature/{Module}/`.
- Tests run against an **in-memory SQLite DB** (`phpunit.xml` sets `DB_CONNECTION=sqlite`, `DB_DATABASE=:memory:`), with mail/queue/cache/session drivers swapped to array/sync equivalents. `BCRYPT_ROUNDS` is dropped to 4 for speed.
- `RefreshDatabase` is the standard trait on feature tests that touch the DB.
- Livewire components are tested with `Livewire::test(ComponentClass::class)->set(...)->assertSee(...)`, not through raw HTTP requests to their host route.
- Most tests build their own fixture data inline (roles, module_access, regions/districts/departments/job titles, employees) rather than relying on factories — factories only exist for the newer Transport module models and `User`. Follow the existing inline-builder pattern (see `tests/Feature/Staff/EmployeeDeactivationTest.php` for a representative example: `createStaffUser()` / `createEmployee()` helper methods) when adding tests for older modules, and use factories when adding tests for Transport.
- `Notification::fake()` is used liberally to avoid hitting real mail during tests that trigger user creation/invites.

Run tests:
```bash
php artisan test                 # full suite, colorized
php artisan test --filter=Name   # single test/class
composer run test                # same as above, clears config cache first
```

## Running migrations / local setup

```bash
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate              # creates database/database.sqlite tables (touch the file first if it doesn't exist)
php artisan db:seed              # runs DatabaseSeeder: roles -> permissions -> module_access -> per-module role/permission seeders -> TransportSeeder -> HolidaySeeder -> SuperAdminSeeder
npm install
npm run build
```

Or the one-shot composer script: `composer run setup`.

Local development (serves app + queue listener + log tail + Vite, all concurrently):
```bash
composer run dev
```

Other useful commands:
```bash
php artisan route:list --except-vendor    # inspect the full route table
php artisan migrate:fresh --seed          # nuke and rebuild the local DB
php artisan gwcl:auto-checkout-visitors   # manually run the visitor auto-checkout job
php artisan leave:forfeit-expired-carry-over --dry-run   # preview annual carry-over forfeiture (drop --dry-run to apply)
php artisan schedule:work                 # run the scheduler locally (visitor checkout, carry-over forfeiture, transport expiry checks)
```

Seeding order matters: `DatabaseSeeder` runs `RoleSeeder` and `PermissionSeeder` before any module-specific role/permission seeder, and `SuperAdminSeeder` last. Two seeders (`LeavePermissionsSeeder`, `LeaveRolePermissionSeeder`) exist in `database/seeders/` but are **not** called by `DatabaseSeeder` — they're legacy/superseded by the migration-embedded seeding described above; don't assume they run.

## Known rough edges (verified against current code)

- `UserFactory` still writes a `name` column the users table no longer has (it has `full_name`), so `User::factory()` fails; the Transport record factories (`VehicleExpenseFactory`, `VehicleIssueFactory`, `MileageLogFactory`) default to it, so pass `recorded_by` / `reported_by` / `driver_id` explicitly (see `tests/Feature/Transport/TransportTestCase`).
- `App\Http\Controllers\Leave\LeaveRequestController` references a `leave.access` middleware alias and a singular `$user->hasRole()` method that don't exist elsewhere in the codebase (`User` only defines `hasRoles()`, plural), and the controller isn't referenced anywhere in `routes/web.php`. Treat it as dead/legacy code, not a pattern to copy.
- Two separate `EnforcesModuleAccess` traits exist (`Http/Controllers/Concerns` and `Livewire/Concerns`) with identical intent — they are not shared, so a fix to module-access logic needs to be applied in both places.
- `UacController` has some commented-out legacy code blocks left in place (e.g. in `store()`) — safe to ignore/clean up but don't be confused by it when reading the file.
- `APP_DOCUMENTATION.md` / `docs/` predate the Assets and Transport modules; don't treat their silence on those modules as "not implemented."
